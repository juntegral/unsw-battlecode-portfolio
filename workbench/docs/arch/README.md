# docs/arch: 다이어그램 우선 개발 (2026-10-01 사용자 결정)

사용자(11:40께): "다이어그램은 한번 적용하는 게 좋을 것 같다. 실제 개발을 할 때도 그걸 기반으로 해 줘."

## 왜
지금까지 가설이 맞아도 구현에서 다르게 움직인 원인은 넷이다.
1. **점수 항의 세기:** 새 규칙은 점수판에 항 하나를 더하는 것이다. 다른 항보다 약하면 발동해도 행동이 바뀌지 않는다. v1.1의 전선 당김 0.12가 그랬다.
2. **규칙끼리 덮어쓰기:** 인계 뒤 옛 규칙이 머리를 되돌렸다(v1.4 개막). 동률 규칙이 가운데를 통째로 내줬다(v1).
3. **결과만 따라 하기:** 상위권의 결과(가운데 54%)를 목표로 줘도, 그 결과를 만든 조건(머리 수, 재분열, 교환 조건)이 없으면 재현되지 않는다(v1.4 지키기).
4. **봇이 아는 세계와 실제 세계의 차이:** 시야 7×7, 음파 id 잘림, 부분 목격, 왕 정의 다섯 개.

## 개발 절차(새 기제마다, 모든 에이전트)
1. **꽂을 자리 그리기:** `flow-*.md`에 새 기제가 들어갈 마디를 표시한다. 무엇을 덮어쓰고 무엇에 덮어쓰이는지(`overrides.md`)도 적는다. 이 단계는 구현 전에 사전 등록과 함께 커밋한다.
2. **세기 정하기:** 새 항의 크기를 `terms.md`의 다른 항과 비교해 정한다. 근거를 한 줄 쓴다. 예: "확실한 진주 하나는 +1이고, 거리 3의 진주 다섯 개 끌림은 약 3.4다. 그래서 칸당 0.4 당김은 진주 무리에 묻힐 수 있다. 위협은 인접 −30, 왕 −45다."(`terms.md`)
3. **예상 그림:** 구체적인 장면 1–2개(지도, 편, 라운드 구간)에서 기대하는 판면을 글이나 ASCII로 적는다.
4. **실제 그림:** 구현 뒤 같은 장면의 실제 기보를 `node eval/board.js <replay> <Map> <a|b> <A|B> <rounds>`로 뽑아 예상과 나란히 놓는다. 다르면 위 넷 중 어느 원인인지 적는다.
5. **세 단계 확인:** 발동했는가(표식), 의도한 상태가 바뀌었는가(판면·칸별 몫), 결과가 바뀌었는가(사슬·승패). 셋을 따로 보고한다.
6. **문서 갱신:** 버전마다 흐름도와 표를 고친다. 문서와 코드가 어긋나면 문서를 먼저 고친다.
