Team meow · The qualifier loop · Oct 4, 2026

An idea in.
A better bot out.

Drop an idea → the loop asks you a few questions.

Check 2–3 replays → it gets tested.

Read what happened → human authors decide; AI ideas decide themselves.

You + one other press OK → merge to main. Then one member uses /submit + confirm to upload.

The loop is the script + AI that takes work from our board and brings decisions back to us. A card is one GitHub issue: the idea or task, its replies, replays and results stay together. AI ideas need one human OK.

One status:* label says what happens next. The loop checks the board about every three minutes and resumes from that label. Routine progress stays on GitHub; meowbot pings when a person needs to act.

  2. Answer: use /answer card:N text:... for questions, replay checks and decisions after results. Your reply appears on the card and publicly in #meow.
  3. Look: when meowbot pings you, open the 2–3 attached replays. Use /answer card:N text:looks right if the behaviour matches your idea, or say what is off. A replay is a saved game you can watch move by move. How to open a .replay →
  4. Read: the result starts with three plain lines, then a “why” table and the per-set numbers. Tasks show identity and their own check instead of outcome A/B.
  5. Decide: use /answer card:N text:ship it / drop it / revise: …, or explain why the evidence is inconclusive. For an online pair request, use /meow.
  6. Approve: press OK on the meowbot candidate card, then confirm. Human cards need the author + one other; AI ideas need one human OK. Approval applies to that exact code revision.
  7. Optional online check: the previous version and new bot play the same higher-elo teams (elo is the ladder rating) on the same maps within about an hour, then we swap back. 준싱 runs the command after approval; you check the report and replays.

Use /loop or /board in Discord to check card states. This page describes the proposed flow; those views and the GitHub card show what is actually running.

What comes next

Idea → release

  1. /hypo → card appears as status:untested. ⏸ waits for you: agree to run it; replace the label with status:ready on GitHub.
  2. Loop asks questions → ping. ⏸ waits for you: /answer card:N text:... → build. Zhe’s ideas always get questions; other ideas only if unclear.
  3. Build → ping with 2–3 replays. Zhe’s ideas ⏸ waits for you: /answer card:N text:looks right → tests. Say what is off to request a revision. Other authors’ look step auto-proceeds.
  4. Result → status:tested. Human authors use /answer card:N text:ship it / drop it / revise: …, or explain why it is inconclusive. The runner interprets the reply. AI ideas decide themselves; close calls wait for people.
  5. Candidate → Discord card. Author + one other press OK → Confirm → merge to main (AI ideas need one human OK). Then one member uses /submit → confirm to upload.

/hypo-max → a fuller card

  1. Choose an area, fill the form → AI reads code, past attempts and game evidence. Usually about 5–15 minutes, plus queue time.
  2. Success → the bot creates an untested card automatically, with findings, test ideas and risks, then posts it and a short summary in #meow. The human proposer stays the author.
  3. No copying into /hypo needed. ⏸ waits for you: review/edit the card, then mark status:ready on GitHub → follow the idea chain. If analysis fails, no card is created.

Task card → approval

  1. GitHub [Task] template → untested. ⏸ waits for you: agree and mark status:ready.
  2. Build + same-play check + the task’s own check → result on GitHub. If unclear: questions → ⏸ waits for you, /answer. No replay approval or outcome A/B.
  3. status:tested → ⏸ waits for you: /answer card:N text:ship it / drop it / revise: … → candidate / rejected / revision → candidate needs author + one other OK → Confirm. Check GitHub for task results; no automatic task ping yet.

Online comparison → swap back

  1. ⏸ waits for you: request the comparison on the card and agree who runs it. 준싱 runs the pair command after approval; the loop does not start it itself.
  2. Oct 4 agreement: post “testing online now” in Discord before starting. Only one person swaps bots at a time. Others wait for the finish message.
  3. Previous version plays → wait for all games → new bot plays the same teams/maps → wait → restore and verify the previous bot → post “done, swapped back”. Never swap with games pending.
  4. Report + replays → ⏸ waits for you: area owner + one other decide on the card. The pair has restored the old bot; keeping the new one needs an authorised activation.

/answer in three lines

Use any language; your words are posted without translation: /answer card:10 text:if an enemy gets in, leave through the other portal

The GitHub comment says Answer from <name>: …. Everyone sees your reply and its link in #meow; you also get a private receipt.

Any teammate can answer for another member’s card. Reply to meowbot’s ping in your own words or use /answer; /meow covers everything else. Other Discord chat is not copied.

05

Just talk to it: /meow

What it is: a teammate you can ask or tell things in plain words, any language. /meow opens a thread; replies there continue the chat.

What it can do: everything the slash commands do; move a card to ready or record a decision; queue a local test or an online 30:30 comparison; use your own branch as a card’s code; explain results; draft a card from a chat.

How actions run: it shows what it will do → you press confirm → meowbot does it. Votes and answers are always yours, never someone else’s.

Not sure → queue: if it needs a judgment call it can’t make, it queues it and asks the team. See /meow queue or /status.

Try saying

/meow Set #16 ready and queue a local test.

/meow Use my branch zhe/safezone2 for #16.

/meow Queue an online 30:30 comparison for #16.

/meow 帮我解释 #16 的结果，再把这个想法整理成卡。

06

Force (when you can’t wait)

Force lives on candidate cards (the Force button) and in /meow force #31 …; submit cards also have Force. There is no separate Force post after each card ping. Any member can use it. /meow force … takes one Confirm and records your message as the reason; the Force button asks for a one-line reason, and sending it is the last step.

It is posted publicly as ⚠️ forced by <name>: <reason> and written on the card.

A forced merge of bot code gets an automatic “still plays the same when off” check afterwards. It only warns; it does not undo the merge.

Nobody can force reading keys, ranked requests, deleting things or changing team rules.

Time zones: take responsibility instead of waiting.

07

What happens at each step, in detail

Times below are planning estimates for the Mac, not measured promises. Queue time, retries and human replies add time. Questions and approvals never time out. All quoted comments are examples, not live results.

untested

You + team

A few minutes to write; wait for agreement.

Write the change, why it matters and what would show it is wrong. For a task, name a concrete completion check. The new card waits until we agree to run it.

What you see · example
“Idea: feed nearby allies late in the game. Watch these two replays.”

Moves on when: We agree to run it → ready.

ready

Loop

Usually the next 3-minute poll, once a slot is free.

Tasks → people take turns (Zhe, QWQ, 준싱) → AI ideas get every 4th slot. Oldest task first; least recently served person first, oldest card within that author. AI also runs when no human idea is ready.

What you see · example
Board: status:ready → status:building. No routine Discord ping.

Moves on when: Zhe’s ideas → questions. Other ideas and tasks → build if clear; questions if unclear.

needs-info

AI → you

About 5–10 min to draft; your reply has no deadline.

AI asks 2–4 concrete edge-case questions under “Questions before we build”. meowbot mentions you. Reply with /answer card:N text:...; your original words appear on the card and publicly in #meow. Zhe’s tasks only need questions if unclear.

What you see · example
“Who should receive the food? What if an enemy is nearby? Should a trapped donor still try?”

Moves on when: Your answers make the intended behaviour clear → building. Ambiguous replies mean another question, not a guessed yes.

building

AI + independent runner check

Ideas: roughly 20–60 min. Tasks: about 30–60 min including checks.

Idea: add a toggle that starts off, compile the bot, and compare toggle-off play with the previous version. Task: implement it as it will ship, with the task active, and run its own check. In both cases the runner independently checks the old 10 maps × 2 seeds × both sides = 40 comparisons. A seed reproduces the random setup. We require the same actions and events, not just the same winner.

What you see · example
“Build passed. Identity: 40/40 identical to the previous version.” Task: “Encryption check passed; play unchanged.”

Moves on when: Idea passes → needs-look. Task passes identity + its own check → tested. Failure → ready with evidence. A task that changes play must be fixed or become an idea card.

needs-look

AI → you

Roughly 15–30 min to run/pick; 5–10 min for you to watch.

Run about 16–32 games total across 2–4 maps where the behaviour should show. AI picks the 2–3 most telling replays, with rounds and what to watch; meowbot brings them to Discord. Zhe confirms his ideas. Other authors auto-proceed, and may still flag a problem. Tasks skip this step.

What you see · example
“Zhe, watch rounds 180–210: the donor reaches its ally. Is that what you meant?” Reply: “looks right” / “No, it should wait.”

Moves on when: /answer card:N text:looks right → testing. Reply with what needs changing → building. “Thanks” alone is not confirmation.

testing

Loop / AI

A few hours on the Mac; one batch at a time.

Local A/B means comparing two versions under matching conditions. The previous version and new bot each play the previous version, on the same maps, seeds and starting sides. Sets: 80 held-out generated maps × 2 sides = 160; their transposed copies = 160 (rows and columns exchanged); and old 10 maps × 8 = 80 (four seeds, both sides). That is 400 games per bot, 800 total. Held-out means not used to design the change. Tasks skip outcome A/B.

What you see · example
Board: “Held-out set done; transposed set running.” Paired + = only new won; − = only previous won.

Moves on when: All sets complete → result comment → tested. Missing games stay incomplete. Around ±8 per 160 can just be luck; it is a rough warning, not a universal statistical cutoff.

tested

Human / AI author

About 5–15 min to read; decide when ready.

Results are ready, not accepted. Read the three summary lines, the “why” table and each set’s numbers. Tasks show that play stayed the same and the task’s own check passed; their authors decide. AI idea cards decide themselves: if the change barely fired or never saw its target, revise once; if that happens again, close as inconclusive. Clear loss → closed; clear win with the intended behaviour and old-map checks → candidate; coin flip → people. A human OK is still needed to merge.

What you see · example
“What we tried: late feeding.
Did it work: intended handoff seen; top-team benefit untested.
Who decides now: Zhe — candidate, drop or inconclusive.”

Moves on when: Human authors reply through /answer: ship it → candidate, drop it → rejected, revise: … → revision, or explain inconclusive evidence. AI ideas follow the rules above; merging still needs human OKs.

candidate

AI prepares · team approves

About 5–15 min to review, plus waiting for OKs and release checks.

AI opens a PR (code to review). Human cards, including tasks, need author + one other OK; AI ideas need one human OK. OK → confirm → merge to main only. Then one member uses /submit and confirms the exact saved version to upload. Changing the PR’s code resets approvals.

What you see · example
“Candidate #42 · needs Zhe + 1 other · [OK] → [Confirm].” Code revision and test evidence are linked.

Moves on when: Current-base checks + required OKs → merge to main → kept. Upload is a separate /submit + confirm. An online pair also needs a human request; leave the previous bot active until its half finishes.

smoke

Human request starts · team decides

About one hour for a 60-game pair, if tickets and game times allow.

Smoke is an optional short online behaviour check. Pick 2–3 higher-elo teams, use --top N, or choose DEV team dev_test_1 (ID 545). ① With the previous version still active, play about 30 unranked games (no ladder rating change). ② Wait until all finish. ③ Upload the approved new bot and play the same teams and map schedule for about 30 more. ④ Wait, then reactivate the previous version. The 60 games use a full hour’s normal unranked allowance; the tool also checks DEV allowance if used. It refuses to start or swap with games live/pending, and stops new requests/uploads after its one-hour window.

What you see · example
“Opponent A: previous / new side by side. Replay IDs: … What changed in the key rounds?” Report includes opponents, lengths and replay IDs for Zhe.

Moves on when: Area owner + one other choose keep or rollback; record kept, rejected or inconclusive. A completed pair restores the previous version; keeping the new bot requires an authorised activation of that exact tested submission. A failed pair may need a manual rollback after pending games finish.

Online pair: 준싱’s commands

Run from unsw-swarm. BOT_DIR contains the new bot’s bot.toml; PAIR_NAME is a fresh name for this check. First verify the active bot is the latest main release. These are instructions, not actions this page performs.

Preview the pair (no upload or game requests):

python3 tools/smoke.py plan BOT_DIR --name PAIR_NAME --pair --top 3 --games 60

After human approval, start; then collect the report:

python3 tools/smoke.py pair BOT_DIR --name PAIR_NAME --top 3 --games 60 --confirm
python3 tools/smoke.py report PAIR_NAME

Manual rollback, once no games are pending:

python3 tools/smoke.py rollback PAIR_NAME --confirm

Instead of --top 3, use --opp 545 for DEV, or --opp ID1,ID2,ID3 for chosen teams. --games 60 is the total, not 60 per bot. --confirm performs real online actions and is only after a human request and confirmation.

kept

No pending action

Final; recorded after the release decision.

The change is accepted and merged to main. Server upload is separate: /submit + confirm. Record the exact merge version and, after upload, its submission ID and previous submission for manual rollback.

What you see · example
“Kept. Released commit …, submission …; previous submission … saved.”

Moves on when: Nothing automatically. Any follow-up is a new card.

rejected

No pending action

Final; a few minutes to record why.

Drop the change and keep the reason with its evidence. If it was uploaded, roll back by hand and record it and verify the previous submission is active.

What you see · example
“Dropped: donors died before the food reached an ally. Replay …”

Moves on when: No next step. A revised idea starts a new card.

inconclusive

No pending action

Final for this attempt; record what is missing.

The evidence did not settle the question. Say what is missing: the intended situation, enough examples, or a useful online comparison. If smoke ran, record whether the previous submission was restored.

What you see · example
“Unclear: no replay showed the intended handoff under pressure. Need that case.”

Moves on when: No automatic promotion. A follow-up card needs new evidence.

08

How we judge a change

Local tests answer: “Is it broken? Does it do what we meant?” They do not prove that we are stronger against top teams. The real test is facing higher-elo teams: a good bot beats most top bots, and there is no single best bot — Zhe’s point. A short online pair gives clues and replays, not a final ranking.

A result comment · mock example

What we tried: feed a nearby ally late in the game.

Did it work: the handoff happened; benefit against top teams is still untested.

Who decides now: Zhe — candidate, drop or inconclusive.

Then comes the “why” table. These are the fields to expect, not made-up measurements. Missing data must say “not measured”.

WhyPrevious versionNew botWhat to ask
Our longest vs their longest at game endBoth lengths + gapBoth lengths + gapDid our deciding dragon improve relative to theirs?
Total lengthBoth teams’ totalsBoth teams’ totalsWhere did the rest of the growth go?
By map familyGames, wins, lengths for each layout familyGames, wins, lengths for each layout familyIs a gain hiding a loss on another kind of map?

Below that: per-set paired + / −, results by starting side, seeds, game counts, uncertainty, toggle settings, exact version IDs and replay links. “We grew more” is not enough if the opponent grew even more. Human authors decide their cards; AI ideas decide themselves, with close calls left to people. Task results instead explain identity and the task’s own check.

09

Rules that keep us safe

  • New behaviour starts behind a switch that is off. With it off, play must be exactly the same as the previous version. Tasks are checked with the task active.
  • No per-map tricks or reliance on map orientation. Qualifier maps are unseen.
  • One test batch at a time. Human-waiting cards do not block unrelated work.
  • The loop never uploads by itself or requests ranked games. OK merges to main; /submit + confirm uploads. Online comparisons need a human request. Rollbacks are done by hand.
  • Rollbacks are done by hand, using the saved previous submission. Wait for pending games before swapping.
  • Record the previous version’s exact commit. If main changes, refresh old-base evidence before shipping. Multiple new toggles also need a short combined check.
  • Freeze: Oct 8, 20:00 KST = Oct 8, 22:00 AEDT. Normal submissions, including smoke, stop; manual rollback is allowed. Force needs the responsibility steps above.
  • Qualifier closes: Oct 9, 15:00 KST = Oct 9, 17:00 AEDT. All dates here are 2026.

A day in the loop

One imagined Zhe idea, before the freeze. KST throughout. This is a possible schedule, not a promise or an actual test result.

  1. 09:00–09:15
    Idea + questions. Zhe uses /hypo: “feed nearby allies late.” AI asks about danger and distance; Zhe answers.
  2. 09:15–10:00
    Build + identity. AI adds the off switch; the runner confirms 40 identical comparisons against the previous version.
  3. 10:00–10:30
    Small run + look. 16–32 games; Zhe watches 2–3 replays and says “that’s what I meant.”
  4. 10:30–14:00
    Local A/B. About 400 games per bot. The loop posts three summary lines, the why table and each set’s numbers.
  5. 14:00–14:20
    Decision + approval. Zhe proposes candidate and asks for smoke. Zhe + QWQ OK and confirm the exact revision.
  6. 14:20–15:20
    Optional pair + final call. 30 previous + 30 new games, then restore previous. The area owner + one other review the opponent report and choose keep, drop or inconclusive.

A clear task card can fit into a 30–60 minute build/check slot, then go straight to the author’s decision and approval. No replay-viewing or outcome A/B detour.
